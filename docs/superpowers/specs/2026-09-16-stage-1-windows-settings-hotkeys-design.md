# Этап 1 — окна, настройки, хоткеи

Дата: 2026-09-16

Первый из четырёх этапов. Задача этапа — не новые возможности, а каркас:
привести в порядок геометрию окон, перестроить настройки так, чтобы в них было
куда класть переключатели этапов 2–4, и сделать назначение хоткеев честным.

## Что не так сейчас

**Все окна открываются не на том мониторе.** `makeWindow()` заканчивается на
`window.center()`, а `center()` ставит окно по центру главного экрана. При
нескольких мониторах это всегда экран с меню-баром, независимо от того, где
работает пользователь.

**Размеры заданы в абсолютных точках** — редактор 980×680, история 720×510,
настройки 590×470, выбор окна 590×460. На встроенном экране 1512×982 редактор
занимает почти весь экран, на 2560×1440 выглядит окошком в углу. Ни одно окно не
запоминает размер и положение между открытиями.

**Отказ регистрации хоткея молча проглатывается.** В `HotKeyManager.registerAll()`
результат `RegisterEventHotKey` проверяется только чтобы решить, сохранять ли
ссылку; при ошибке не происходит ничего, и пользователь видит назначенное
сочетание, которое не работает.

**Конфликты с чужими хоткеями никак не видны.** Проверено на macOS 26.4:
`RegisterEventHotKey` возвращает `noErr` даже для ⇧⌘3, ⇧⌘4 и ⇧⌘5, занятых самой
системой. Регистрация формально удаётся, но системные сочетания обрабатываются
раньше приложений, и нажатие до Snipiko не доходит.

## Решения

### 1. Геометрия окон

Новый тип `WindowPlacement` описывает, как открывается каждое окно:

```swift
enum WindowPlacement {
    case editor, history, settings, picker, permission

    var autosaveName: String     // ключ для запоминания рамки
    var fraction: CGSize         // доля от visibleFrame экрана
    var minSize: NSSize
    var maxSize: NSSize
}
```

| Окно        | Доля        | Минимум  | Максимум  |
|-------------|-------------|----------|-----------|
| Редактор    | 0.80 × 0.80 | 680×480  | 1800×1150 |
| История     | 0.62 × 0.60 | 620×440  | 1400×900  |
| Настройки   | 0.52 × 0.58 | 640×480  | 1000×760  |
| Выбор окна  | 0.50 × 0.52 | 560×420  | 900×700   |
| Разрешение  | фиксированное 480×360 — это диалог, масштабировать нечего |

Порядок при открытии:

1. Экран назначения — тот, на котором курсор (`NSEvent.mouseLocation`), с
   откатом на `NSScreen.main`.
2. Попытаться восстановить прошлую рамку через `setFrameUsingName`.
3. Если рамка восстановилась, но не пересекается ни с одним `visibleFrame` —
   монитор отключили — считать её негодной и перейти к шагу 4.
4. Иначе размер = `visibleFrame.size × fraction`, зажатый в `[minSize, maxSize]`,
   и центрирование на экране назначения.
5. `setFrameAutosaveName` — дальше AppKit сам запоминает изменения.

Проверка: замерять получившиеся рамки на всех трёх мониторах и сверять с
расчётом; отдельно — что после ручного изменения размера и переоткрытия рамка
сохраняется, а после удаления ключа autosave считается заново.

### 2. Настройки

`TabView` заменяется на `NavigationSplitView` — список разделов слева, как в
Системных настройках macOS. Разделы этапа 1:

- **Основные** — запуск при входе, состояние доступа к записи экрана.
- **Съёмка** — формат, качество JPEG, автосохранение и папка. Сюда лягут
  переключатели этапа 2.
- **Хоткеи** — назначения, конфликты, проверка сочетания.

Раздел «История» появится на этапе 4, когда в нём будет содержимое. Пустых
разделов не создаём.

Внутри разделов — `Form` со `Section`, у каждой секции поясняющий футер вместо
россыпи `Divider`, как сейчас.

### 3. Хоткеи

**Показывать отказ регистрации.** `registerAll()` начинает возвращать список
действий, которые зарегистрировать не удалось. Настройки показывают их явно,
рядом с соответствующей строкой.

**Предупреждать о заведомо занятых сочетаниях.** Динамический список
недоступен: приложение в песочнице, и проверено, что `UserDefaults(suiteName:)`,
`CFPreferencesCopyAppValue` и прямое чтение
`~/Library/Preferences/com.apple.symbolichotkeys.plist` возвращают пусто —
домашняя папка подменяется на контейнер. Поэтому в код кладётся статический
список общеизвестных системных сочетаний macOS:

| Сочетание | Занято |
|-----------|--------|
| ⇧⌘3 | Снимок всего экрана в файл |
| ⌃⇧⌘3 | Снимок всего экрана в буфер |
| ⇧⌘4 | Снимок области в файл |
| ⌃⇧⌘4 | Снимок области в буфер |
| ⇧⌘5 | Панель съёмки экрана |
| ⌘Space, ⌃Space | Spotlight и смена раскладки |
| ⌘Tab, ⌘Q, ⌘W | Системные действия |

Список бьёт по частым случаям, но не знает о том, что пользователь переназначил
системные сочетания сам, и ничего не знает о сторонних программах. Поэтому он
только предупреждает, не запрещая.

**Проверка сочетания — главный механизм.** Кнопка «Проверить» рядом с
назначением: пользователь жмёт своё сочетание, приложение ждёт до пяти секунд и
отвечает фактом — дошло нажатие или нет. Это работает против любого
перехватчика, включая сторонние программы, про которые узнать заранее нельзя.

Реализация: `HotKeyManager` получает режим проверки. Пока он включён,
срабатывание хоткея **не выполняет действие**, а только поднимает флаг — иначе
проверка сочетания съёмки области делала бы снимок при каждом нажатии. По
истечении пяти секунд режим выключается сам.

Базовый ответ не требует никаких разрешений: сработал зарегистрированный
хоткей — сочетание доходит до Snipiko; не сработал — не доходит.

Различить «перехватывает кто-то другой» и «вы просто не нажали» можно только
глобальным монитором `NSEvent.addGlobalMonitorForEvents`, а он требует
Accessibility. Разрешение остаётся необязательным: без него проверка отвечает
«сочетание до Snipiko не дошло» и предлагает выдать доступ для уточнения
причины. Требовать Accessibility нельзя — работа глобальных хоткеев без него
заявлена как свойство приложения в README.

## Чего этот этап не делает

Не добавляет ни одной новой возможности съёмки, не трогает историю, редактор и
превью сверх того, что нужно для геометрии окон. Курсор в кадре, звук и вспышка,
шаблон имени, закрепление поверх экрана, «поделиться», распознавание текста,
поиск и избранное — этапы 2–4, каждый со своим дизайном.

## Порядок работ

1. `WindowPlacement` и новое размещение окон — самая изолированная часть, ничего
   не ломает и сразу проверяема замерами.
2. Отказы регистрации хоткеев — маленькая правка, от которой зависит UI настроек.
3. Перестройка настроек на боковое меню, включая показ конфликтов и отказов.
4. Проверка сочетания — последней, потому что опирается на готовый раздел.
